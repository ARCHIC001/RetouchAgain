# 发布范围、环境与复现缺口

> 发布派生版/非历史原稿。本文是发布快照的范围说明，不复制现场接手原稿，也不承接原实验资格。

## 1. 发布仓库承担什么

发布物用于阅读方法、分析算法代码、审查状态与执行边界，并在独立环境中逐步重建依赖。
源码是一个时间点的发布快照，不是附带现场文件和授权的完整运行环境。
方法可用性意味着关键机制和职责足够清晰，不意味着克隆后立即调用模型/后端。
发布目录与原工作区独立；导出不删除、移动或压缩替换原知识资产。

## 2. 本次允许进入的材料

- 经逐文件允许清单选取的原创算法/实现源码。
- 经重新组织、去除现场叙事与敏感内容的方法说明。
- 发布仓库 README，以及导出/检查工具明确允许的必要文件。
- 唯一明确授权的 DSC_3734 三文件示例：原始NEF、普通作者目标JPG、o前缀基础预览，保留 `paired photos/DSC_3734/` 布局与原始字节（含元数据）。三文件共35,225,397 B，不包含原尺寸作者备份或实验输出；用途与ICC见README。

文件进入依据是职责和内容审核，不是“扩展名看起来像代码”。
原源码仍可能包含现场引用、固定单任务假设或研究依赖，需结合环境检查理解。
允许导出源码不表示所有原 Markdown、JSON 或 PDF 都自动属于发布范围。

## 4. DSH 与执行后端缺口

`dsh_photo_runtime.mjs` 从单独的 DSH 安装载入 agent/session/llm 等能力。
源码不包含该安装，也不假设发布仓库是 DSH 自身的上游分发。
worker 还依赖原生后端的实际控件、命令、设置读回和完整渲染接口。
需要核查 API 兼容性、控件目录、源相关单位、真实结果 schema 与输出合同。
名称相同或能 import 不证明实际接口一致。

发布入口保留特定单任务和现场协议假设，不是通用任意图像命令行产品。
这些假设的识别与替换需要单独工程工作，不能用缺失配置的默认值“碰巧跑通”。
外部操作人员也不应在恢复过程中代替 DSH 每轮挑参数来伪装自主闭环。

## 5. 图像工具链缺口

Python 图像链涉及 Pillow、NumPy、LittleCMS 及部分 TIFF/编解码依赖。
源转换还可能依赖单独安装的 RAW/DNG 转换工具与相机颜色信息。
当前依赖加载器针对固定的外部依赖目录；发布物不附带该安装目录。
不自动下载或运行第三方安装脚本，不把临时依赖路径当正式跨平台方案。

发布副本做了有限的路径去身份变换，详见根目录 `publication-scope.json`：
- JS 的个人 Python 回退路径改用 `VISHARNESS_PYTHON` 或 `python`，已有 `runtime.python` 优先级不变。
- 显式原尺寸作者查找改由 `VISHARNESS_FULL_AUTHOR_ROOT` 提供；默认短边副本职责不变。
- DNG 转换器路径由 `VISHARNESS_DNG_CONVERTER` 或外部安装占位提供。
- 含个人身份的临时 TIFF 依赖搜索路径移除；环境需另行安装依赖，固定依赖加载器的要求也仍保留。`photo_input_contract.py` 另有基于 home 的历史 Windows 临时回退，未改为跨平台安装承诺。
- `photo_stage_schema.py` 仅移除一处行尾空格，不改变算法。Git 仓库按 `.gitattributes` 将文本行尾统一为 LF；这也不等同于原现场字节资格。

这些仅作用于发布副本，原工作区冻结源码不变；发布副本不能冒充原冻结字节/mtime 资格。
共享基础模块中的历史 `SYSTEM`、旧 compact helper 与其 CLI 仍作为被复用代码的一部分保存，
不因此成为当前受支持入口；当前阶段运行只由 `dsh_stage_run.mjs` 组合。

可独立检查的入口为 `check_photo_stage_tasks.py`、`check_photo_stage_operations.py`、
`check_photo_stage_schema.py`、`check_photo_phase_workflow.py` 和 `check_photo_stage_continuation.py`。
在已单独准备 Pillow/NumPy 的可信 Python 环境中，以 `python -I -B -X utf8 src/<入口>` 执行。
它们使用合成/临时夹具，不读取真实照片或调用模型、Native；测试通过也不补齐下述现场缺口。

RAW 支持是按真实编码/IFD/颜色与几何核查的资格，不是按后缀通吃。
synthetic 输入覆盖逻辑分支，不能替代真实相机编码与后端解码验证。
颜色和几何合同见[观察与色彩](observation-and-color.md)。

## 6. 冻结教材与历史记录缺口

部分工具知识检索、完整预检和 prepare/freeze 路径引用现场冻结教材与基础记录。
本发布范围排除这些记录，所以完整预检可能在读取依赖前停止，而不是全部可运行。
缺项应在环境检查中明确报告；不能生成空文件或虚构“已通过”来绕过。
纯函数/合成检查可作为独立工程检查，但需准确说明是否实际调用模型或 Native。

原源码/原稿中的“当前”“冻结”“已验证”属于其写作和实施时点。
本发布文档不继承原运行次数、费用、成功率、作者认可或图像效果结论。
工程 complete、目标 partial、JPEG 确认和作者选择是不同事实维度。

## 7. mtime、Git 与资格

原现场某些检查用字节数、mtime 和记录 ID 检查冻结源码/资源是否变化。
Git clone、解压或复制会改变文件时间，也不保留原现场的完整资格链。
即使文件名或字节数相同，也不据此宣称原素材、后端、设置与授权已经恢复。
不修改 mtime 伪装通过，不借旧 freeze 文件给新环境追认资格。

本次不运行或重算哈希。
核对采用文件职责、允许清单、实际内容/画面、尺寸、设置读回与独立记录身份。
独立环境若要运行，需要新的输入资格、实际基线、图像角色审阅和明确资源安排。

## 8. 建议恢复顺序

1. 先阅读[架构](architecture.md)、[资源协议](protocol-and-resources.md)和本页的排除范围。
2. 在不读取凭据、不调用模型/Native 的情况下检查源码依赖和外部安装缺口。
3. 单独准备兼容运行时及图像依赖，明确安装来源与适用权限。
4. 先运行可独立执行的纯函数/合成检查，记录限制；不重建原成绩。
5. 如确需真实输入，再另行许可基线制备、读回和完整分辨率图像资格。
6. 如确需收费模型，再建立新 scope 和显式授权；工程恢复本身不授权收费。

本次发布不执行上述真实恢复步骤，也不自动续跑旧任务。
