# 系统架构：基于单一视觉 Agent 的分级调色闭环

RetouchAgain 是一个用于**图像后期调色与参考图仿色（Color/Tone Matching）**的多轮视觉 Agent 框架。它将摄影师的修图过程拆解为“看图对比 → 诊断差距 → 规划调色步骤 → 执行小步参数调整 → 验证实际画面变化”的串行闭环，每一步修改都有据可查、可回退。

## 1. 系统分层与协作方式

整个系统采用**“单一大脑决策 + 确定性宿主状态机”**的架构：

```text
当前观察图（双图） + 工作包上下文
        │
        ▼
  DSH Agent（视觉分析 / 更新建议库 / 选择细组与参数）
        │
        ▼  photo_stage_turn（单回合复合提交）
  宿主校验层（当前阶段权限 / 参数单位与范围 / 蒙版 ID）
        │
        ▼
  原生图像后端（写入参数 / 读回实际设置 / 全分辨率渲染）
        │
        ▼
  Python 状态机（记录版本树 / 派生下一轮观察图）
```

- **DSH Agent（决策层）**：负责所有视觉推理与审美判断——识别当前图与目标图的明暗/色彩差距、决定先调什么、给出具体参数、评估上一步改得好不好、决定回退还是进入下一阶段。
- **Python 状态机（`src/dsh_stage_worker.py`）**：系统的唯一权威状态源，负责管理阶段流转、版本树（父子关系）、建议库（Proposal Bank）以及真实执行账本。
- **JS 运行与适配层（`src/dsh_stage_run.mjs`、`src/dsh_stage_adapter.mjs`）**：负责对接外部 DSH 模型能力、组装每轮发送的工作包、管理 PNG 图像附件，并动态替换当前阶段可用的工具 Schema。
- **原生后端（Native Backend）**：实际执行调色命令、返回读回参数（DevelopSettings）并完成全分辨率图像渲染。

## 2. 分级工作流：G1–G4 检查点与三阶段分支

调色最容易遇到的问题是影调和色彩互相耦合——曝光一动，饱和度和色相观感全变。RetouchAgain 通过**“先定影调、再调色彩、最后联合收尾”**的三阶段结构把问题解耦，并在阶段之间设置了 4 个全局检查点（`G1`–`G4`）：

| 环节 | 观察输入 | 核心任务与产出 |
|---|---|---|
| **G1（初诊）** | 彩色目标图 vs 后端基线 `v0` | 识别明暗、色彩、局部耦合问题及需保护的区域，初始化建议库 |
| **Tone（影调）** | 统一灰度目标图 vs 当前图（或父/子图） | 在剥离色彩干扰后专注调整曝光、反差、曲线与局部光影，选出最佳影调版 |
| **G2（色彩重评）** | 彩色目标图 vs 影调选中版 | 基于定稿的影调重新评估色彩差距，更新色彩任务优先级 |
| **Color（色彩）** | 彩色目标图 vs 当前图（或父/子图） | 逐组调整白平衡、校准、HSL 与色彩分级，同时监测是否破坏既有影调 |
| **G3（综合验收）** | 彩色目标图 vs 色彩选中版 | 审查整体协调性、影调回退情况与局部边界，收敛出少量综合残差 |
| **Joint（联合微调）** | 彩色全图及局部 ROI | 针对 G3 发现的残差做影调/色彩/质感联合精修，选版并导出最终 JPEG |
| **G4（交付确认）** | 彩色目标图 vs 实际导出的 JPEG | 基于真实导出文件做最终验收（标记为已确认、部分达成或需返修） |

工作流支持按需回退：**G2 可退回 Tone，G3 可退回 Tone 或 Color，G4 可退回 Joint**。一旦从 G4 退回修改，旧的 JPEG 验收状态会自动失效，必须重新导出并观察新图后才能再次确认。

## 3. 任务组织：Issue → 分支 → 模块 → 细组

为了避免 Agent 一次乱改十几个滑块导致效果不可解释，RetouchAgain 将调色动作组织为五层结构：

1. **Issue（问题）**：画面中的具体缺陷或差距（如“暗部死黑”“天空偏青”）。
2. **Branch（分支）**：归属到 `Tone`、`Color` 或 `Joint`。
3. **Module / Step（模块/步骤）**：对应调色面板中的功能区。
4. **Fine Group（细组）**：围绕同一摄影假设的一组协同控件（例如“高光+白色色阶”、“Master 点曲线”或“同一个局部蒙版下的参数”）。
5. **Turn（回合）**：针对选定细组的多轮微调与效果验证。

各分支的默认推荐路线如下（Agent 可根据画面瓶颈灵活跳步、提前处理局部问题或回访）：
- **Tone**：曝光 → 对比度 → 高光/阴影 → 白场/黑场 → Master 点曲线 → 参数曲线 → 局部影调蒙版 → 收束。
- **Color**：G2 重评 → 全局白平衡 → 相机校准（Calibration） → 全局饱和度/HSL → 色彩分级（Color Grading） → 局部白平衡 → 收束。
- **Joint**：仅针对 G3 留下的具体残差，按需组合影调、色彩、曲线、质感（Texture/Clarity/Dehaze）或局部微调。

## 4. 单回合复合提交（`photo_stage_turn`）

为了减少无意义的来回确认，Agent 每轮通过 `photo_stage_turn` 一次性提交四个动作：
- **`review`**：对比当前两张图，给出上一轮操作效果的判断。
- **`bank_delta`**：对建议库执行增、删、改、延后或结案。
- **`selected_issue_id` / `selected_group_id`**：声明本轮要推进的问题和细组（以及跳步/重排理由 `selection_reason`）。
- **`action`**：执行具体的调色操作、请求局部放大图、检索历史、切换阶段、选版或导出。

每次执行调色修改时，都必须附带一个**五字段预期**：目标（`target`）、预期变化（`expected_change`）、保护区域（`protected_region`）、风险点（`risk`）和反证条件（`falsifier`），方便下一轮客观复核。

## 5. 计划状态与客观事实分离

状态机将“模型打算做什么（`current plans`）”和“系统里真实发生了什么（`actual`）”严格分开：
- 参数修改采用**绝对赋值**，且每次写入后都会从后端读回实际值入账。
- 当 Agent 决定回退到早期某个更佳版本时，状态机不会删除后续分支的历史，而是保留版本树结构，并将废弃分支上未完成的复核项标记为分支外状态。

## 6. 核心源码地图

| 模块 | 职责 |
|---|---|
| `src/dsh_stage_run.mjs` | 主循环入口与阶段流程串联 |
| `src/dsh_photo_runtime.mjs` | 外部 DSH 运行时接入与会话投影 |
| `src/dsh_stage_adapter.mjs` | 模型请求封装、Schema 校验反馈与回执诊断 |
| `src/dsh_stage_worker.py` | 权威状态机、复合提交处理与操作编排 |
| `src/photo_phase_scheduler.py` | G1–G4 阶段调度、返修回退与跨阶段复核债务 |
| `src/photo_stage_tasks.py` | 模块注册表与默认路由依赖解析 |
| `src/photo_proposal_bank.py` | 建议库管理、执行账本与工作包构建 |
| `src/photo_stage_schema.py` | 动态生成当前阶段的提交 Schema |
| `src/photo_stage_operations.py` | 阶段控件白名单校验与蒙版原子事务 |
